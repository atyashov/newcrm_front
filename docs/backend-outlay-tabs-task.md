# Задача: API вкладок раздела смет

Дата: 2026-10-17.

## Цель и границы

Подготовить бэкенд для вкладок dashboard: «Сметы», «Поступления», «Операции»,
«Распределение», «Самовывоз/самовозврат», «Возвраты», «Текст».
Источник требований: обновлённый OldCrm, раздел modules/admin/outlay.
Этот документ описывает задачу, а не уже реализованный контракт.
Предложенные ниже новые названия полей и маршрутов нужно зафиксировать
в серверной документации после реализации. Существующие контракты не ломать.

Не входят: переписывание фронтенда, перенос старых данных, PDF/Word,
публичный просмотр сметы, SMS, AMO, задачи сотрудников и архив смет.

## Текущее состояние

- POST /api/admin/outlays: список, фильтры, сортировка, пагинация.
- POST /api/admin/outlays/store, GET/PUT/DELETE /api/admin/outlays/{id}: CRUD.
- Сохраняются execution_date, return_date, date_comment, responsible_workers,
  оплаты и предоплаты, группы и товары. Список возвращает уникальные stores.
- Есть CashLedgerService: движения по сметам, расходам и займам, корректировки.
- GET /api/admin/cash-boxes/{id}/transactions: пагинация журнала одной кассы.
- GET /api/admin/cash-boxes/summary: финансовая сводка по подразделению и периоду.
- Нет self_pickup/self_return, отдельного примечания возврата, четырёх групп
  назначенных сотрудников и статусов обработки позиций.
- В OutlaysFilter return_date сейчас задаёт только верхнюю границу возврата.

## Общие требования к API

- Авторизация и права по принятой архитектуре проекта.
- Любой список ограничивать доступными пользователю подразделениями на сервере.
  Без subdivision_id нельзя возвращать данные недоступных подразделений.
- Для смены сметы/назначений/статусов проверять доступ к самой смете;
  переданный subdivision_id не заменяет эту проверку.
- Кассы могут быть общими, не привязывать их принудительно к подразделению.
  Финансовые строки отбирать по подразделению исходного документа, не кассы.
- Формат ответа: существующий {status, errors, data}.
- Пагинация: data.items с data, current_page, last_page, per_page, total, from, to.
  Принимать page и page_size, сохранять поддержку существующих алиасов.
- Сортировка: существующий sort=field / sort=-field; whitelist полей,
  стабильная дополнительная сортировка по ID.
- Денежные значения возвращать десятичными строками, вычислять без float.
- Даты периода включают оба граничных дня. Указать серверный часовой пояс
  и единый формат дат/времени в документации. Не подменять дату события created_at.
- Итоги рассчитывать по всей отфильтрованной выборке, не текущей странице.
- Избежать N+1: сотрудники, статусы, кассы, документы-источники, склады и
  агрегаты этапов загружать пакетно. Не требовать запрос по каждой смете/позиции.
- Ошибки валидации: 422 и errors с ключами полей; отказ доступа: 403.

## Этап 1. Рабочие списки смет

### 1. Поля и назначения

Добавить в смету:

| Поле | Тип | Назначение |
| --- | --- | --- |
| self_pickup | boolean, default false | Самовывоз |
| self_return | boolean, default false | Самовозврат |
| return_date_comment | nullable string/text | Примечание ко времени возврата; аналог return_time |

Существующий date_comment остаётся примечанием ко времени заказа.
Самовывоз и самовозврат независимы: разрешены все четыре комбинации.
Не определять эти признаки по адресу или тексту примечаний.

Добавить независимые множественные назначения на users:

| Входное поле | Связь в ответе | Назначение |
| --- | --- | --- |
| performer_ids | performers | Исполнители заказа |
| return_performer_ids | return_performers | Исполнители возврата |
| assembler_ids | assemblers | Сборщики заказа |
| acceptor_ids | acceptors | Приёмщики заказа |

Каждый массив: integer, distinct, exists:users,id; проверка допустимости
назначения пользователя по правилам доступа проекта. Отсутствующее поле
в запросе обновления сохраняет назначения, [] явно очищает их.
Новые поля необязательны для старого фронтенда.
responsible_workers и creator_id сохранить: это отдельные сущности,
не переносить их автоматически в исполнителей/сборщиков.

В GET одной сметы и списке возвращать ID-массивы и связанные объекты пользователей
минимум с id, login, firstname, lastname. Пароли/токены не возвращать.
Также возвращать объект статуса и создателя для отображения без запросов по строкам.

### 2. Расширить существующий список POST /api/admin/outlays

Добавить фильтры:

- id: точный ID сметы.
- self_pickup и self_return: boolean, корректно обрабатывать false/0.
- return_date_from, return_date_to: независимый диапазон по return_date.
- status_ids: массив ID статусов; внутри массива OR.
- performer_ids, return_performer_ids, assembler_ids, acceptor_ids:
  внутри одного массива «назначен хотя бы один из выбранных».
- store_ids: смета содержит хотя бы один товар выбранного склада.
- return_date_comment: поиск по подстроке.

Разные фильтры объединять AND. Существующие фильтры не менять.
Если одновременно переданы status_id и status_ids, отклонять запрос с 422,
чтобы избежать неочевидного пересечения.
Пустые массивы фильтров не ограничивают выборку.
Фильтры связей не должны дублировать сметы и ломать total/pagination.
Разрешить сортировку как минимум по execution_date, return_date, id, title, status_id.
Сохранить старое значение return_date как верхней границы для совместимости.

### 3. Быстрые изменения

Предлагаемые маршруты:

- PATCH /api/admin/outlays/{id}/status: {status_id}.
- PATCH /api/admin/outlays/{id}/assignments: один или несколько массивов назначений.

Не требовать title, client_id, groups и прочие поля полной формы.
Возвращать обновлённую смету/назначения и статус.
Не очищать остальные поля и не переписывать товарные позиции.
Изменение статуса обязано запускать существующую складскую синхронизацию,
если affects_stock меняется; не обходить WarehouseService.
Повтор одинакового запроса не должен создавать повторные движения/резервы.
Все изменения выполнять транзакционно.

### 4. Правила вкладок (новые отдельные маршруты не обязательны)

| Вкладка | Запросы и отбор |
| --- | --- |
| Распределение: заказы | execution_date в выбранном дне, по возрастанию времени |
| Распределение: возвраты | return_date в выбранном дне, по возрастанию времени |
| Самовывозы | Как заказы распределения + self_pickup=true |
| Самовозвраты | Как возвраты распределения + self_return=true |
| Возвраты | return_date в диапазоне, фильтры статусов/сотрудников/складов |

Обычное «Распределение» в legacy включает также самовывозы/самовозвраты:
не исключать их без отдельного решения заказчика.
День распределения по умолчанию текущий; это не месячный финансовый период.
Верхняя таблица отображает date_comment, нижняя return_date_comment.
Одна смета может попасть в обе таблицы, если обе даты соответствуют отбору.

## Этап 2. Финансовые вкладки

### 5. Поступления

Предлагаемый маршрут: GET /api/admin/outlays/receipts.
Зарегистрировать статический маршрут до GET /outlays/{outlay}.

Одна строка на актуальную предоплату или окончательную оплату:

- Стабильный ключ строки (например, outlay:ID:prepayment/final_payment).
- outlay_id, outlay_title, execution_date, subdivision_id.
- type: outlay_prepayment / outlay_payment.
- occurred_at, amount, cash_box: {id,title}, payment_method: {id,title}.

Предоплата: prepayment=true, сумма prepayment_amount, дата prepayment_date.
Окончательная оплата: is_paid=true, сумма total_cost минус активная предоплата,
дата date_of_paid. Нулевой остаток отдельной строкой не выводить.
Смета 1000 с предоплатой 300 и полной оплатой даёт 300 + 700, а не 300 + 1000.

Фильтры: subdivision_id, date_from/date_to по occurred_at, type, cash_box_id,
payment_method_id, outlay_id, outlay_title, execution_date_from/execution_date_to.
Сортировка: occurred_at, amount, outlay_id, execution_date.
data.totals.amount: сумма по всей выборке с теми же фильтрами.
Период поступлений относится к дате оплаты, а не дате заказа.

### 6. Операции

Предлагаемый маршрут: GET /api/admin/cash-boxes/operations.
Зарегистрировать до /cash-boxes/{cashBox}.

Для соответствия legacy основной список строить по актуальным документам:
оплаты/предоплаты, расходы, исходящие и входящие займы.
Не выдавать необработанный cash_box_transactions за этот список:
журнал содержит дельты и автоматические сторнирования.
Существующий /{cashBox}/transactions оставить отдельным аудит-журналом.

Строка: стабильный ключ, type, direction (income/expense), положительный amount,
signed_amount, occurred_at, subdivision_id, cash_box, source_type, source_id,
source_title; для сметы также outlay_id и execution_date.
Типы: outlay_payment, outlay_prepayment, expense, borrowing_sent, borrowing_received.
Расход/исходящий займ отрицательны в signed_amount; поступление/входящий займ положительны.
У межподразделенческого займа каждая сторона относится к своему подразделению.
В общей выборке обе стороны допустимы: это две кассовые операции, не дубли.

Фильтры: subdivision_id, date_from/date_to по дате операции, type, direction,
cash_box_id, source_type/source_id, source_title; диапазон даты заказа для смет.
Сортировка: occurred_at, amount, type. Общая пагинация после объединения источников.
data.totals: income, expense (обе положительные), net (со знаком),
по всей выборке с применёнными фильтрами.
После изменения/удаления документа список и итоги должны отражать актуальное состояние.
Не копировать ошибки знаков займов из старого OperationsSearch.

### 7. Согласованность со сводкой

Использовать общую логику сумм с CashBoxesSummaryService, а не независимые формулы.
При одинаковом подразделении и периоде поступления/расходы/займы должны
сходиться с соответствующими показателями сводки.
Не включать начальный остаток кассы в список поступлений от смет.

## Этап 3. Этапы обработки товарных позиций

Это отдельный функционал, не блокирующий выпуск вкладок без плашек готовности.

### 8. Хранение и обновление

Для каждой позиции сметы предусмотреть состояния:
assembled (собран), uploaded (погружен), retrieved (забран), checked (проверен),
lost (утеря), defective (дефект).
Хранить автора и время изменения; обеспечить одно актуальное состояние на позицию.
Предлагаемый PATCH /api/admin/outlays/{id}/items/{itemId}/stages принимает
только изменяемые флаги. Проверять принадлежность позиции смете и права пользователя.
Не менять резерв/остаток товара автоматически по этим флагам:
связь с реальными складскими движениями требует отдельного согласования.

### 9. Агрегаты складов в списке смет

Дополнить каждый объект stores полем stages:

```json
{
  "id": 1,
  "title": "С15",
  "stages": {
    "total": 10,
    "assembled": 10,
    "uploaded": 4,
    "retrieved": 0,
    "checked": 0,
    "lost": 0,
    "defective": 1
  }
}
```

Считать уникальные позиции сметы, не сумму quantity, как в legacy.
Для первых четырёх этапов: 0 = не выполнено, 0<count<total = частично,
count=total = выполнено. Утерю/дефект показывать при count>0.
Пустое значение не должно ошибочно означать готовность.
Агрегировать пакетно для страницы. Смена склада товара должна соответствовать
существующему правилу формирования stores; исторические снимки складов в эту задачу не входят.

## Вкладка «Текст»

Отдельный endpoint не обязателен после добавления диапазона возвратов.
Фронт сможет получить все страницы заказов и возвратов за нужный период,
объединить события по времени и сформировать копируемый текст.
Возвращать title, address, execution_date, return_date, date_comment,
return_date_comment, id. Возврат не должен зависеть от попадания заказа в тот же период.
Само текстовое форматирование и ссылки остаются на фронте.

## Критерии приёмки и тесты

- Миграции безопасны для существующих смет; новые флаги false, назначения пустые.
- Старый payload полной формы продолжает работать, новые необязательные поля не теряются.
- [] очищает только указанную группу сотрудников, отсутствующее поле сохраняет её.
- Самовывоз и самовозврат фильтруются независимо; false не игнорируется.
- Проверены границы суток/месяца, null return_date, возврат в другом месяце, чем заказ.
- Несколько назначений/складов не дублируют строки и не завышают pagination.total.
- Проверены чужие подразделения, подмена ID сметы/позиции, недопустимые назначения.
- Быстрое изменение статуса не меняет товары/оплаты и корректно синхронизирует склад.
- Проверены оплаты: без предоплаты, частичная, полностью покрывающая итог,
  изменение суммы/даты/кассы, снятие оплаты и удаление сметы.
- Проверены знаки расходов и обеих сторон займа; общие кассы не раскрывают чужие документы.
- Итоги финансовых списков не зависят от страницы и согласованы со сводкой.
- Проверены состояния этапов 0/часть/всё и отсутствие N+1 на больших списках.
- Добавить API/feature-тесты и документацию с примерами запросов/ответов,
  доступными sort-полями, фильтрами, часовым поясом и правилами прав доступа.
