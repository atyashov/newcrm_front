# Пользователи и подразделения: контракт фронтенда

Разделы фронтенда: `/users` и `/subdivisions`.
Бэкенд при этой реализации не изменялся. Ниже указаны необходимые доработки по состоянию на 17.10.2026.

## Общий контракт списков

REST-маршруты уже существуют: `/api/admin/users` и `/api/admin/subdivisions`.
Используются GET списка, GET `/{id}`, POST, PUT `/{id}`, DELETE `/{id}`.
Авторизация передаётся общими методами `apiGet/apiPost/apiPut/apiDelete`.

Параметры списка: `page`, `page_size` (по умолчанию 20), `sort` (поле или `-поле`) и непустые поля фильтра.
Ожидаемый ответ: `{status: true, data: {items: {data: [...], current_page, last_page, per_page, total, from, to}}}`.
Сейчас оба API возвращают полный массив `data.items` и не обрабатывают параметры списка.
До доработки бэкенда фронтенд фильтрует, сортирует и разбивает полный массив локально.
После перехода на paginator фронтенд использует серверные метаданные без повторной локальной обработки.

Фильтры пользователей: `firstname`, `lastname`, `login`, `email`, `phone`, `status`.
Сортировка пользователей: `id`, `firstname`, `lastname`, `login`, `email`, `phone`, `status`.
Фильтры подразделений: `title`, `amo_ids`, `sms_sender_name`, `site_link`.
Сортировка подразделений: эти же поля и `id`.
Строковые фильтры подразумевают поиск по подстроке, `status` — точное совпадение.

## Пользователи

POST/PUT передаёт:

```json
{
  "firstname": "Имя",
  "lastname": "Фамилия",
  "login": "admin",
  "email": "admin@example.com",
  "phone": "+70000000000",
  "status": "1",
  "role_id": 1,
  "subdivision_ids": [5, 6]
}
```

POST и PUT передают `password` только при заполнении. Поля пароля при загрузке пользователя всегда пустые; существующий пароль/хеш никогда не подставляется в форму.
`password_confirmation` проверяется на фронтенде и отправляется на сервер вместе с непустым `password`. При пустом пароле оба поля отсутствуют в запросе обновления.
Пустой пароль в PUT отсутствует в payload; существующий хеш должен сохраняться. При создании пароль обязателен.
Сервер требует подтверждение пароля (`confirmed`). Требования к сложности пароля проверяются на сервере независимо от фронтенда. Статус в форме задаётся галочкой «Активен» и отправляется как `status`: `1` или `0`.
Роль выбирается одна, поэтому сохранение выполняется через `roles()->sync([$roleId])`.
Полный справочник ролей загружается постранично из `admin/roles`.

Необходимо на бэкенде:

1. Валидировать `subdivision_ids` как массив уникальных целочисленных ID существующих подразделений. Проверять право назначать выбранные подразделения и выбранную роль, не допускать повышения привилегий без соответствующего разрешения.
2. Синхронизировать `subdivisions()->sync(...)` в транзакции с сохранением пользователя и роли. Если `subdivision_ids` отсутствует в PUT, не изменять связи; пустой массив означает явное снятие всех связей.
3. В GET списка и GET одного пользователя возвращать `roles: [{id, title}]`, `role_id` и `subdivisions: [{id, title}]` либо дополнительно `subdivision_ids`. Сейчас список содержит роли, но не подразделения; детальный ответ не загружает ни одну из этих связей.
4. Не перезаписывать `status` безусловно значением `1` в `UserService::save`. Валидировать `0/1` и сохранять присланное значение.
5. Добавить серверную фильтрацию, сортировку и пагинацию по контракту выше. Список для селектов ответственных сотрудников должен сохранить существующий контракт и не потерять пользователей при добавлении пагинации основного списка.
6. Проверить политики для чтения одного пользователя и удаления: сейчас show/destroy не вызывают authorize явно, а DELETE не имеет middleware `can:delete,user`.

Защита фронтенда: если при редактировании подразделения отсутствуют в обоих ответах (список/детальный), выводится предупреждение. Пока пользователь не изменил селект, `subdivision_ids` не отправляется, чтобы не стереть неизвестные связи.

Текущий DELETE пользователя отключает его (`status = 0`), а не удаляет строку. Фронтенд отображает фактический статус и позволяет фильтровать активных/отключённых. Если ожидается исчезновение записи, требуется определить отдельный серверный контракт удаления/архивации.

## Подразделения

POST/PUT передаёт `title`, `amo_ids`, `logo`, `description`, `default_product_group_id_for_amo`, `sms_sender_name`, `site_link`.
`title` обязателен. `logo` — относительный путь файла из менеджера, не объект файла и не base64; без логотипа передаётся null.
`description` содержит HTML из существующего Quill-редактора. При выводе HTML на бэкенде/в просмотре требуется безопасная очистка.
`amo_ids` — строка ID через запятую. `site_link` — обычная строка без URL-валидации на фронтенде.

Необходимо на бэкенде:

1. Добавить `site_link` в `$fillable` модели Subdivision: сейчас поле возвращается из БД, но игнорируется при сохранении через fill.
2. Дополнить валидацию остальных полей, допустимых длин и nullable-значений; `logo` разрешать только в доступном файловом хранилище, не допускать произвольных путей.
3. Реализовать серверные фильтры, сортировку и пагинацию. Селект в шапке и селект доступа пользователей уже подготовлены к загрузке всех страниц.
4. Добавить пункты меню `users` и `subdivisions` и соответствующие разрешения. Фронтенд маршруты существуют независимо от серверного меню.

## Группа по умолчанию для AMO

В legacy `default_product_group_id_for_amo` выбирается из `OutlayGroupName::listAll()`, затем записывается в `outlayGroup.group_name_id`.
Это ID справочника `outlay_group_names`, не ID экземпляра группы конкретной сметы `outlay_groups`.
Текущий `admin/outlay-groups` требует конкретную смету и подразделение, поэтому не подходит для этого селекта.

Фронтенд загружает весь справочник через `admin/outlay-group-names` для каждого доступного подразделения, по 100 записей на страницу до последней страницы. Подпись содержит название группы и подразделения; дубликаты удаляются по ID.
Для нового подразделения доступны существующие группы доступных подразделений, как в глобальном legacy-списке.
На бэкенде нужно подтвердить допустимость выбора группы другого подразделения либо предусмотреть общий справочник/копирование. Не подменять это поле ID из `outlay_groups`.
При ошибке загрузки справочника сохранённый ID не сбрасывается, селект блокируется; остальные поля можно сохранять.

## Вход

Фронтенд теперь отправляет `{login, password, session_time}` на `pub/auths/login`, а не поле `email`.
Поле имеет тип text и подпись «Логин». Это соответствует текущему `LoginRequest` бэкенда (`login: required|string|max:90`).
