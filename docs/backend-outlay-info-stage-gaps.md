# Страница info: статусы и недостающие возможности legacy

Проверено 2026-10-20 по modules/admin/views/outlay/info.php старого проекта
и текущим OutlayItemStage, UpdateOutlayItemStagesRequest, OutlayService.
Бэкенд в рамках задачи не изменялся.

Обновление: перечисленные ниже доработки реализованы сервером и подключены на
фронте. Комментарии читаются из items[].comments, заметки из item.work_notes,
авторы и даты каждого поля/флага из editors[field]. Сохранение текста при blur
отправляет только изменённое поле; пустое значение отправляется как null.
Ошибка не удаляет черновик, доступно повторное сохранение. При применении ответа
обновляется только соответствующее поле и его метаданные: соседние параллельные
изменения не затираются. Общий редактор строки остаётся лишь fallback для старых данных.

## Уже поддерживается и подключено на фронте

На внутренней странице /outlays/:id/info у каждой позиции показаны шесть галочек:
assembled, uploaded, retrieved, checked, lost, defective.
GET info уже возвращает groups[].items[].stages и updated_by/updated_at.
PATCH /api/admin/outlays/{id}/items/{itemId}/stages сохраняет только изменённый флаг.
Пока запрос идёт, галочки этой позиции заблокированы; другие позиции доступны.
При ошибке сохраняется подтверждённое состояние, ошибка видна рядом с позицией.
Полная смета не пересохраняется; состав, количество, цены и платежи не меняются.
Статусы недоступны клиенту на публичной странице.

Флаги булевы на всю позицию. Частичную обработку 7 из 10 стульев не изображаем.
В интерфейсе показывается последний редактор строки статусов, а не автор каждого
отдельного этапа: нынешний контракт не позволяет различать этих авторов.

## Что добавить на сервере для соответствия старой info

### 1. Комментарии позиции

В legacy отдельно сохранялись assembly_comment (комментарий по сборке)
и retrieve_comment (комментарий по забору), у каждого свой автор.

Предложение: PATCH /api/admin/outlays/{outlay}/items/{item}/comments
с необязательными nullable string полями assembly_comment/retrieve_comment.
Отсутствующее поле не менять, пустое/null явно очищает комментарий.
Валидация длины (например, 10000), минимум одно присутствующее поле.
Ответ: data.item с обновлёнными комментариями и безопасными данными авторов/времени.
Включить эти данные в info; исключить из публичного API.

### 2. Общие рабочие заметки сметы

В legacy были поля:

- additional_upload_comment: «Дополнительно собрано».
- retriever_comment: «Комментарии для забора».
- damage_loss_comment: «Порча / Утеря».

Предложение: PATCH /api/admin/outlays/{outlay}/work-notes с частичным обновлением
этих полей, автором/временем каждого изменения. Возвращать в info, не в публичном
API. Обычное редактирование сметы не должно очищать заметки.

### 3. Автор и время по отдельному флагу

В legacy у каждого из шести флагов был собственный автор. Сейчас updated_by
общий для всех шести: после изменения «Дефект» теряется информация, кто ранее
отметил «Собран». Добавить метаданные для каждого флага, например:

```json
{
  "assembled": true,
  "editors": {
    "assembled": {"user":{"id":7,"login":"worker"},"updated_at":"2026-10-20 10:00:00"}
  }
}
```

Общий updated_by/updated_at оставить для совместимости. Сохранять только
действительно изменённые поля; повтор такого же запроса не меняет автора/дату.
Метаданные фиксировать и при снятии отметки. Полную историю событий при
необходимости делать отдельно: последнее значение автора не заменяет аудит.

## Общие требования

- OUTLAYS_MANAGE и доступ к фактическому подразделению сметы.
- Проверка принадлежности позиции смете; защита от подмены item ID.
- Транзакции, частичные обновления без потери несвязанных полей.
- Клиент не задаёт автора/время; они определяются сервером.
- Операционные комментарии не подменять публичным description товара.
- Не изменять остатки/кассы при сохранении заметок или флагов.
- Не создавать автоматических действий на основании «Утеря»/«Дефект» без
  отдельного ТЗ по складскому учёту.
- Не придумывать авторство старым флагам при миграции; неизвестные авторы null.
- Feature-тесты прав, чужих позиций, очистки/частичного изменения, повторных
  запросов и отсутствия этих данных в публичном ответе.
